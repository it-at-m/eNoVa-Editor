The **eNoVa-Editor** is a specialized desktop assistant for municipal caseworkers (*Sachbearbeiter/innen*) in Germany to process electronic preemptive right inquiries (*Vorkaufsrechtsanfragen*) submitted by notaries via the **beBPo** (*Besonderes elektronisches Behördenpostfach*).

Starting in **January 2027**, municipalities in Germany are legally required under the eNoVA act (*eNoVA-Gesetz*) to process preemptive right requests digitally in the structured **XJustiz 2900003** format. The eNoVa-Editor enables caseworkers to view incoming inquiries in a readable format, capture municipal decisions under the German Federal Building Code (*Baugesetzbuch – BauGB*), and generate standard-compliant response datasets (**XJustiz 2900003 Sachentscheidung**) as well as printable decisions (PDF/HTML).

---

## Architectural Principles & Key Features

- **Strict Separation of Code and Layout**:
  - Layout and styling are maintained entirely in customizable template files (`Input.htm` for inquiries and `Output.htm` for decisions/certificates).
  - Data binding is achieved declaratively via `{{xpath:...}}` and `{{codelist:...}}` expressions—local IT administrators can easily customize layouts, municipal coats of arms (*Wappen*), and official seals (*Dienstsiegel*) without compiling any Java code.
- **Dynamic XJustiz Codelists (Genericode XML)**:
  - Decision types and role descriptions are loaded dynamically from official Genericode XML files (`codelists/ENOVA.Sachentscheidung-1.0.xml`, `codelists/ENOVA.ErsuchenSachentscheidung-1.0.xml`, `codelists/GDS.Rollenbezeichnung-3.5.xml`). No hardcoded Java enums are used.
- **Schema-Free Caseworker Configuration**:
  - `caseworkers.xml` holds native XJustiz XML snippets (`<tns:auswahl_beteiligter>...`) in CDATA sections, allowing any valid XJustiz participant structure without rigid Java schema constraints.
- **XJustiz 2900003 Response Transformation**:
  - In accordance with the XJustiz standard, both the incoming request and the outgoing municipal decision belong to message type **2900003** (`tns:nachricht.enova.entscheidung.2900003`).
  - The response is generated by transforming the incoming message (replacing `ersuchenSachentscheidung` with `sachentscheidung` and assigning municipal sender/file number details), ensuring 100% preservation and consistency of notarization, parcel, and participant data.
- **Generic PDF & HTML Bescheid Generation**:
  - Output decisions are rendered to `Output.htm` and converted to PDF without any hardcoded layout code or legal terminology inside the Java codebase. Caseworkers can also print directly from their browser (`window.print()`).
- **High-DPI & Screen Scaling Support**:
  - Dynamic window positioning and responsive layouts prevent off-screen borders on multi-monitor or scaled setups (125% / 150% Windows DPI).

## Workflow Overview

```
[Notary via beBPo] ──> [XJustiz 2900003 XML] ──> [eNoVa-Editor]
                                                        │
                      ┌─────────────────────────────────┴─────────────────────────────────┐
                      ▼                                                                   ▼
       [XJustiz 2900003 Sachentscheidung]                                   [Official Decision (PDF/HTML)]
              │                                                                   │
              ▼                                                                   ▼
   [Qualified Signature (qeS)]                                            [Municipal File / E-Akte]
   (CAdES detached .p7s / .pkcs7)                                         (Behördliche Veraktung)
              │
              ▼
  [Return to Notary via beBPo]
  (Forwarded to Land Registry / GBO §§ 29, 137)
```

## Building and Running

### Prerequisites

- **Java Development Kit (JDK) 21** or later (e.g. Eclipse Temurin 21)
- **Apache Maven 3.9+** (or the included `./mvnw` wrapper)

### Build Standalone Distribution

To build the application and package a standalone distribution with a bundled runtime:

```bash
# Windows
.\mvnw.cmd package -Pdist

# Linux / macOS
./mvnw package -Pdist
```

The self-contained distribution is located in `target/distribution/eNoVa-editor`. It contains a minimal Jlink Java runtime, all configuration files, templates (`Input.htm`, `Output.htm`), and sample data.

### Running the Application

Double-click `eNoVa-editor.cmd` in the distribution folder, or run:

```bash
target\distribution\eNoVa-editor\eNoVa-editor.cmd
```

You can also pass an XML file directly:

```bash
target\distribution\eNoVa-editor\eNoVa-editor.cmd samples\xjustiz_beispiel_2900003.xml
```

## Deutsch / German

Der **eNoVa-Editor** ist ein Fachassistent für Sachbearbeiterinnen und Sachbearbeiter in den Bau- und Liegenschaftsverwaltungen deutscher Kommunen zur digitalen Bearbeitung von Vorkaufsrechtsanfragen der Notare über das **beBPo** (*Besonderes elektronisches Behördenpostfach*).

Ab **Januar 2027** sind Kommunen gesetzlich verpflichtet, Vorkaufsrechtsanfragen der Notariate digital im strukturierten Format **XJustiz.enova.2900003** nach dem eNoVA-Gesetz zu verarbeiten. Der eNoVa-Editor ermöglicht die lesbare Anzeige eingegangener Notaranfragen, die Erfassung der Sachentscheidung nach BauGB und die rechtskonforme Erzeugung der Antwortnachricht (**XJustiz 2900003 Sachentscheidung**) sowie des Bescheids (PDF/HTML).

### Architektur & Designprinzipien

1. **Strikte Trennung von Layout und Code (`Input.htm` & `Output.htm`)**:
   - Die Gestaltung von Eingangsanzeige und Bescheid-Ausgabe erfolgt vollständig in editierbaren HTML/CSS-Dateien.
   - Platzhalter werden deklarativ über `{{xpath:...}}` und `{{codelist:...}}` aufgelöst.
   - Örtliche Administratoren können Wappen, Briefköpfe, Gebührenregelungen und Satzungstexte anpassen, ohne Java-Code neu kompilieren zu müssen.
2. **Dynamische Genericode-Codelisten**:
   - Sachentscheidungen und Rollenbezeichnungen werden zur Laufzeit aus den offiziellen XJustiz-XML-Codelisten geladen (`codelists/ENOVA.Sachentscheidung-*.xml`).
3. **Schemafreie Sachbearbeiter-Konfiguration**:
   - `caseworkers.xml` nimmt native XJustiz-Fragmente (`<tns:auswahl_beteiligter>`) im CDATA-Block auf.
4. **Fachliche XJustiz-Konformität (2900003)**:
   - Sowohl Eingang (Ersuchen um Sachentscheidung) als auch Ausgang (Sachentscheidung) gehören zur Nachricht `tns:nachricht.enova.entscheidung.2900003`.
   - Die Antwort wird direkt durch Transformation des Eingangs-XML gebildet, sodass Urkundendaten, Notarangaben und Flurstücke 100 % konsistent bleiben.
5. **Generische PDF- & Druckausgabe**:
   - Bescheide werden aus `Output.htm` gedruckt oder generisch in PDF gewandelt—ohne hardcodierten Layout-Code in Java.
